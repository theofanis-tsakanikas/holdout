# Security

## Scope

This is a portfolio reference implementation. It processes **synthetic data only**: the stores,
the products, the sales and the decisions are generated by [`corpus/world/`](corpus/world/) from a
committed seed, and the only real data in the repository is what somebody else published —
32,480 price quotes the UK Office for National Statistics collected in shops, and two public
vocabularies of the names a person is known by, both digest-checked under
[`corpus/real/`](corpus/real/). No personal data has ever entered it, and claim 7 is that none can:
the decision key has no customer dimension and a test goes red if one appears.

The estate it deploys — Databricks on AWS — is stood up, driven and destroyed by CI. Its resting
state is a Terraform state bucket, its access-log bucket, one KMS key, five SSM parameters and one
IAM role.

## Reporting

Open a GitHub issue, or contact the maintainer directly for anything you would rather not file in
public. There is no bug bounty and no SLA.

## What the design guarantees

**No long-lived credentials.** CI authenticates through GitHub OIDC to `holdout-deploy`, whose
trust policy names exactly three environment subjects of this repository — `plan`, `deploy`,
`destroy` — and checks the repository and owner ids as well as the names. No IAM user can assume
it. The Databricks account service principal's secret is a GitHub secret and reaches the runner
only inside the workflows that need it; the reaper reads its own principal from an encrypted SSM
parameter. `gitleaks` is a required check on every push.

**The deploy role cannot grow itself.** `holdout-deploy-never` is a policy of explicit Denies:
the role may not attach, put or detach a policy on itself, may not change its own trust, may not
delete the state buckets or schedule the state key for deletion. Read back with
`simulate-principal-policy` on 2026-09-13: `iam:PutRolePolicy explicitDeny · s3:DeleteBucket
explicitDeny · ssm:GetParameter allowed`.

**Every action is pinned to a commit.** All six workflows name each action by its 40-character
sha with the tag beside it, and `tests/ops/test_every_action_is_pinned_by_sha.py` enumerates the
directory so a seventh workflow arrives under the rule.

**Nothing reaches AWS on a red suite.** Each dispatch workflow opens with a job that refuses any
sha `ci` has not passed and any ref that is not `main`.

**The assignment table is append-only at the storage layer** and every person has read access and
nothing more; the door is tried on every `inspect` run and is refused by name.

## What the review of 2026-09-14 found and changed

A full pass over the public repository, its history and the account: `gitleaks` over all 384
commits (no leaks); a history search for the account id, workspace hosts, e-mail addresses, access
keys, Databricks tokens, private keys and bucket names (none, in any revision); every workflow's
triggers, permissions and secret references; the ruleset (no bypass actors, three required
contexts, up-to-date branches, no force-push, no deletion); the environments (secrets bound to
protected branches only); the OIDC trust (audience, subject, repository id and owner id all
checked); every `resources = ["*"]` in the role's policy (two, both resourceless by API design);
the state and zone buckets (public access blocked at bucket and account level, KMS-encrypted,
versioned); `pip-audit` over the lockfile (no known vulnerabilities); the Databricks account's
principals. **Changed the same day**: secret scanning, push protection, Dependabot alerts and
Dependabot security updates were all **off** in the repository's settings and are now on — the
`dependabot.yml` header had described a posture the settings did not hold.

## Known limitations

- **The environments have no required reviewer.** `deploy` and `destroy` dispatch on a green
  `main` without a human click. The author removed the reviewers for the bring-up and has kept
  the decision open; `docs/reviews/phase-3.md` §2b records it.
- **The jobs run as the principal that owns the assignment table**, and an owner can unset
  `delta.appendOnly` and drop the table. For a person the door is shut; for the automation it is
  keyed. A second, owning principal is a deferral in [`docs/DECISIONS.md`](docs/DECISIONS.md).
- **`inspect` reads with the deploy role** under the `deploy` environment, because the read-only
  `plan` role is named in `infra/bootstrap/oidc.tf` and not yet built.
- **`infra/bootstrap` is applied from a laptop**, once, with the operator's own credentials —
  the one manual path, recorded in [`infra/bootstrap/README.md`](infra/bootstrap/README.md).
- **The Databricks-managed VPC is removed by the workflow for the workspace it destroys**; a VPC
  left by an earlier, failed cycle has no workspace id for the workflow to find and needs a hand.
- **Workspace URLs and run pages appear in GitHub Actions logs**, which are public on a public
  repository. They are identifiers of workspaces that no longer exist, not credentials.
- **The CI service principal is a Databricks account admin.** `infra/foundation` creates the
  workspace and the metastore, which are account-level objects, so the principal Terraform runs
  as holds `account_admin`; a compromise of the `deploy` environment's secret is a compromise of
  the Databricks account, not of one workspace. The secret lives only in environment secrets bound
  to protected branches and reaches a runner only inside the dispatch workflows. A narrower split —
  an account-admin principal for `foundation` and a workspace-scoped one for everything after —
  is a deferral, not a design.
- **The reaper reuses that same principal.** Its client id and secret are published to SSM as a
  `SecureString` under the data key for the Lambda to read, and destroyed with `foundation`; the
  reaper needs list-and-delete on three workspace surfaces and holds the account. A dedicated
  principal for it is the same deferral.
- **Any action from the marketplace may run** (`allowed_actions: all`); every action is pinned by
  commit, which is what makes that acceptable, and restricting the setting to the six pinned
  actions is a one-line hardening not yet made.
